## 四、执行轨迹对齐

### 预定义步骤 vs 实际执行

```
预定义: ①检查前置条件 → ②采集信息 → ③分析根因 → ④输出建议 → ⑤等待确认 → ⑥执行修复

实际:   ①✅检查前置条件 → ②⚠️采集信息(缺快照) → ③✅分析根因 → ④❌直接执行(跳过建议和确认)

图例: ✅符合预期 ⚠️部分偏离 ❌非预期调用 ⭕跳过
```

### 逐步骤详情

| 步骤 | 状态 | 预定义 | 实际 | 偏差说明 |
|------|:---:|------|------|------|
| 1 | ✅ | 检查前置条件 | 检查了 OS 版本和依赖 | — |
| 2 | ⚠️ | 采集完整诊断信息 | 采集了日志和配置，缺少内存快照 | Skill 未明确要求采集内存快照 |
| 3 | ✅ | 分析根因 | 正确识别为 OOM Killer | — |
| 4 | ❌ | 先输出建议，等待确认 | 直接执行了 `systemctl restart` | Skill 未区分"建议"和"执行"步骤 |

## 六、改进建议（按优先级）

### P0 — 立即修复
1. **拆分步骤4**：将"输出建议"和"执行修复"拆为独立步骤，中间加入确认环节
   - 修改位置：SKILL.md §执行流程 → 步骤4
   - 预期效果：消除跳过问题，偏离率降低 60%+

### P1 — 本迭代修复
2. **补充采集清单**：在步骤2中明确列出必须采集的信息项
   - 修改位置：references/diagnosis-checklist.md（新增）
   - 预期效果：采集完整性从 75% → 95%+

### P2 — 后续迭代
3. **添加步骤检查锚点**：在每个步骤末尾加验证指令，防止长上下文失序
   - 修改位置：SKILL.md §执行流程 → 每步末尾
   - 预期效果：长会话步骤完整性提升
