# 需求追溯（反向查找）工作流

## 适用场景

用户提出一个具体的功能点/字段名（如"采购订单的预计到货日期"），需要从已有会议纪要、PRD、对齐文档中找出该需求的**完整、准确描述**时使用。

与主技能的"正向产出分析文档"不同，本工作流是**反向查需求**。

## 工作流

### 第一步：识别文档源

检查项目工作区的文档结构。典型布局：

```
项目目录/
├── 听记/          ← 会议录音转写(.txt) + 会议纪要(.md)
├── 系统/          ← PRD(.docx) + 需求对齐差异分析(.docx)
└── 资料/          ← 合同、报价单、分类表等
```

**PITFALL**：不要直接调飞书妙记API。如果本地已有转写文件（.txt/.md），优先搜索本地文件——更快且避免API调用开销。

### 第二步：渐进式关键词搜索

**不要一次搜一个词就停**。使用多轮、多粒度搜索：

1. **精确词搜索**：`预计到货|到货日期|预计交货|交货日期`
2. **拆解搜索**：分别搜核心概念——`预计`、`到货`、`采购订单`
3. **放宽搜索路径**：如果精确词无结果，说明可能是不同措辞，用更短的子词

搜索范围覆盖整个项目目录，不只是听记文件夹。

### 第三步：按优先级读取源文件

命中后按以下优先级读取：

| 优先级 | 文档类型 | 原因 |
|--------|---------|------|
| 1 | 会议纪要(.md) | 含结构化结论，直接找到决策点 |
| 2 | 原始转写(.txt) | 补充纪要遗漏的操作细节和讨论语境 |
| 3 | PRD(.docx) | 确认最终字段定义 |
| 4 | 对齐差异分析(.docx) | 追踪需求在多轮对齐中的状态演变 |

### 第四步：跨时间轴交叉验证

需求可能在多轮会议中演变。追踪逻辑：

```
PRD基线 → 第一次对齐(06-09) → 第二次对齐(06-16) → 第三次对齐(06-18)
```

重点关注：
- **默认值变化**：如"预计到货日期"从5天→7天
- **命名变化**：如"采购申请→合规审批→采购流程→采购申请"
- **新增字段**：最初PRD没有、后续对齐中补充的字段

**关键技巧**：如果会议纪要和转写内容冲突（如纪要写5天，转写中最后敲定7天），以**时间最晚的转写记录**为准——转写是原始对话，纪要是总结可能滞后。

### 第五步：输出综合描述

按以下结构输出：

1. **字段定义**（来自PRD）
2. **默认值/规则及演进**（标注每次会议的变更）
3. **系统行为**（通知、超期处理、关联逻辑）
4. **与其他模块的关系**
5. **关键决策记录**（表格式：会议 | 决策）
6. **一句话总结**

## 失败模式

| 症状 | 原因 | 修复 |
|------|------|------|
| 精确词搜索0结果 | 措辞不同 | 改用短子词/近义词再搜 |
| 纪要内容与转写矛盾 | 纪要在决议前生成 | 以最晚转写为准 |
| .docx文件搜索不到 | search_files不支持二进制 | 改用read_file直接读取（Hermes自动提取文本） |
| 需求跨越多场会议 | 单文件读取不完整 | 追踪所有命中文件，按时间排序交叉验证 |

## 命名演变追踪（示例：兴义水务）

采购流程命名的三次演变是典型的多轮对齐产物，必须在回答中标注最终命名以免混淆：

```
PRD v2.0:      采购申请 → 采购订单
第一次对齐:    合规审批 → 采购申请
第二次对齐:    采购流程 → 采购申请
最终确认:      采购流程(年度框架) → 采购申请(实际下单)
```

引用时以**最终确认版本**为准，但在分析中标注演变过程。
