# 技术方案层级选择指南

> 用于 answer Phase 1 Clarify — 新业务/产品领域的「技术层级」追问维度

## 问题

Agent 在收到"建设系统/平台"类需求时，容易默认使用最轻量的技术方案（SPA + BaaS/Supabase + 静态部署），快速出 Demo。但用户的实际需求可能是企业级原生开发。

## 分层

| 层级 | 名称 | 技术栈特征 | 典型场景 | Agent 行为 |
|------|------|-----------|----------|-----------|
| **Tier 1** | 原型验证级 | 单文件 SPA、BaaS（Supabase/Firebase）、OSS 静态部署 | "快速跑一个 Demo"、"验证想法"、"内部工具" | 快速出 MVP，技术选型不拘泥 |
| **Tier 2** | 企业交付级 | 独立后端（Java/Go/Python）、独立数据库（MySQL/PG）、原生前端（小程序/App/H5 工程化）、CI/CD、等保合规 | "建设系统"、"生产环境"、"对客交付"、"招投标" | 按完整工程规范规划，不抄近路 |

## 触发条件

> Phase 1 Clarify 中，如果用户描述包含以下信号，必须追加「技术层级」追问：

- "建设系统" / "搭建平台" / "开发一个XX系统"
- 涉及支付 / 结算 / 清分 / 交易
- 国企 / 政府 / 金融 / 医疗等合规强监管行业
- 多期规划 / 长期维护 / 招投标
- 用户明确说"原生开发" / "不用 Supabase" / "不是 Web SPA"

## 追问模板

```
Q: 技术方案层级 — 这是原型验证级还是企业交付级？

| 选项 | 说明 |
|------|------|
| A. 原型验证级 | 快速验证想法，SPA+BaaS 轻量方案，1-2天出Demo |
| B. 企业交付级 | 生产级系统，独立后端+数据库+原生前端，按工程规范 |

推荐：根据用户描述的{合规要求/业务复杂度/交付对象}，推荐 {A/B}
```

## 反面案例

**场景**：用户要求"建设票务预定系统+长期综合平台"，涉及支付结算、国企客户、招投标需求

**错误做法**：Agent 默认用 HTML+Supabase 建 DEMO 并部署 OSS，产出"积木式原型"

**用户纠正**："这不是简单的 Web SPA，也不用 Supabase，需要原生开发"

**后果**：DEMO 全部作废，方案需从头重写

**教训**：涉及"系统建设"+"支付"+"国企"三个信号同时出现时，必须追问技术层级，不能默认 Tier 1
