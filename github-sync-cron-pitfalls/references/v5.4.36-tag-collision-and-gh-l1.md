`CURRENT_VERSION` constant. The remote `refs/tags/v5.4.36` already

`c68229d` (v5.4.36's actual content) pushed to main successfully,
but `git tag -a v5.4.36` failed with `tag already exists`.

## Root Cause Analysis

The local `CURRENT_VERSION = '5.4.35'` constant in `scan_inventory.py`
was correct from local perspective (no intervening commits had been
merged to local working tree since the v5.4.35 sync). However, the
remote had been pushed to by an earlier cron (or possibly the same
cron in a previous run that got partially completed) using
`v5.4.36` as the tag. This created a remote tag collision.

**Why this happens**:
- The skill's PATCH bump is computed locally from a hardcoded
  `CURRENT_VERSION`, not derived from `origin/main`'s latest tag
- If the cron is interrupted between push and tag (e.g., the prior
  cron was killed mid-way), the remote tag and remote main can
  diverge
- A subsequent successful cron using the same PATCH bump then
  collides with the orphaned tag

**The diagnostic that surfaced it**:
```bash
git ls-remote origin v5.4.36 refs/tags/v5.4.36
# Output: 791f5e26... refs/tags/v5.4.36
# (different from local HEAD c68229d)
```

## Resolution Applied

Standard force-update of the tag:
```bash
git push origin :refs/tags/v5.4.36  # delete remote tag
git tag -d v5.4.36                    # delete local tag
git tag -a "v5.4.36" -m "v5.4.36 — current commit's message"
git push origin v5.4.36
gh release create v5.4.36 --title "..." --notes-file ...
```

**This is safe** because the cron is the sole committer to
`jorinyang/awesome-skills`. The tag only ever pointed at cron's
own commits. No human/team workflow can be disrupted.

## Recommendation for Future Crons

1. **Replace local `CURRENT_VERSION` constant with a dynamic
   derivation** from `git ls-remote origin --tags --sort=-v:refname`:
   ```python
   def get_next_patch_version(work_dir):
       out = subprocess.run(['git', '-C', work_dir, 'ls-remote',
                              '--tags', '--sort=-v:refname', 'origin'],
                             capture_output=True, text=True).stdout
       # Parse top tag like "v5.4.36", bump PATCH
       ...
   ```
   This eliminates the staleness that caused v5.4.36's tag collision.

2. **Always pre-check tag existence before `git tag -a`**:
   ```bash
   git ls-remote origin refs/tags/v$NEW_VERSION
   if exists && points_at_different_sha; then
     force-update
   fi
   ```
   The diagnostic is cheap and prevents wasted cron cycles.

3. **Default to L1 (`gh release create`) for release creation**,
   not L2/L3. L1 is stable on this host.

4. **Verify working tree is clean AFTER push**, not just before.
   Race conditions where another cron ran between phases can leave
   the tree in a half-state. Add a `git status --porcelain` check
   at the END of Phase 5 to confirm.
