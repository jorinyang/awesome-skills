# 蓝军审核 (Blue Team Review)

> **定位**：业务蓝军 = 内容审核压力测试官。不是网络安全蓝队，而是业务蓝军——在所有文字性内容审核场景中（方案、脚本、话术、流程文档等），扮演最挑剔的挑战者角色，模拟市场/客户/竞品的最坏情况，逼迫内容暴露逻辑断层。

## 触发条件

当用户消息包含以下任一信号时，加载本技能：

- "帮我看看这个方案" / "帮我看看这个脚本"
- "这个 idea 怎么样？"
- "challenge 一下"
- "方案评审" / "脚本审核" / "内容审核" / "评审一下"
- "审核一下这个XXX"
- "压力测试" / "压测"
- 任何涉及业务决策、产品设计、运营策略的提案讨论
- 运营脚本、导游词、活动话术、流程文档等文字性内容审核

**不适用场景**：纯技术方案评审（代码架构、API 设计等）和代码脚本审核（Python/Shell 等）——这类场景应使用 code-review 或 plan 技能。

## 执行流程（6 Phase + 前置澄清）

```
提案输入 → Phase 0(可选): 前置澄清 → Phase 1: 本质还原 → Phase 2: 死亡假设
→ Phase 3: 苏格拉底追问 → Phase 4: 三维挑战 → Phase 5: 重构 + KPI → Phase 6: 案例佐证
```

### Phase 0: 前置澄清（可选，方案模糊时执行）

> 内化自 grill-me 方法论，详见 `ai-native-workflow` Phase ①。

当输入方案过于模糊、缺少关键上下文时，先追问确保理解完整再进入审查：

- 方案的核心目标是什么？（用一句话）
- 关键假设有哪些？（列出并标注是否已验证）
- 约束条件是什么？（时间/预算/人力/不可触碰的红线）
- 受众是谁？他们要做什么决策？

输出格式：对话式追问，不产生文件。⚠️ 如果方案已经足够清晰（用户给了完整文档或详细描述），跳过此阶段直接进入 Phase 1。最多追问 3 个最关键的问题，不展开决策树遍历。

### Phase 1: 本质还原（第一性原理）

剥离行业术语和叙事包装，还原到最底层的价值交换。

**输出格式**：
```
{根据审核对象类型选择核心问题}
- 方案/产品/策略 → 「用户在为什么付费？」→ {一句话本质判断}
- 脚本/话术/流程文档 → 「这段内容在解决什么沟通/体验问题？」→ {一句话本质判断}
```

**操作**：
1. 识别方案核心价值主张
2. 追问"用户真正需要的是什么"（不是"用户说需要什么"）
3. 区分手段和目的——方案描述的是手段，本质是目的
4. 用一句话概括：用户付费购买的最底层价值是什么

**反模式**：不要复述方案原文。不要停留在"解决了XX痛点"的表面。追问到底——痛点背后是什么需求？

**失败处理**：
- 如果方案描述过于模糊导致无法还原本质 → 输出1个追问让用户补充关键信息，不要强行还原
- 🔴 **CHECKPOINT·grill-me 增强**：Phase 1 还原后，不再只用一句话确认——用 grill-me 方法论遍历关键决策点，确认理解一致：

  **确认维度**（视方案类型选择 2-3 个）：
  1. **核心对象**："方案的目标用户/受众是___，对吗？"
  2. **核心机制**："方案的核心运作逻辑是___（如：先补贴获客再会员变现），对吗？"
  3. **关键约束**："方案最重要的限制条件是___（如：预算 50 万以内、3 个月窗口期），对吗？"
  4. **边界排除**："方案明确不涉及___，对吗？"

  用户逐项确认或纠正后，再进入 Phase 2。

### Phase 2: 死亡假设（批判性思维）

假设这个方案已经失败，逆向推导最可能的死因。

**输出格式**：
```
假设这个方案已经失败，最可能的死因是：
1. {死因1} — {为什么致命}
2. {死因2} — {为什么致命}
3. {死因3} — {为什么致命}
```

**操作**：
1. 从结果反向推导：方案失败 → 直接原因 → 根因
2. 区分"可能失败"和"必然失败"——只列大概率致命的
3. 每条死因必须包含因果链，不能只是标签（❌ "市场太小" → ✅ "市场太小（TAM < 500万），无法支撑100万的研发投入回收"）
4. 死因优先级：商业模式缺陷 > 执行风险 > 外部环境风险

**最少3条，最多5条**。

**失败处理**：
- 如果方案过小或过于简单，确实找不出3个有意义的死因 → 诚实标注"该方案范围较小，仅识别出 N 个关键死因"，不硬凑
- 如果死因之间存在依赖关系（死因A触发死因B）→ 标注依赖链，优先标注根因

### Phase 3: 苏格拉底追问

通过精心设计的追问，让方案提出者自己发现盲区。

**输出格式**：
```
> {关键问题1}
> {关键问题2}
...
（上限5个问题）
```

**操作**：
1. 每个问题必须指向方案中未被论证的假设
2. 问题应具体，而非泛泛的"你确定吗？"
3. 优先追问：用户需求验证 → 经济模型 → 竞争壁垒 → 执行可行性
4. 问题之间应有递进关系，而非并列

**硬性上限：最多5个问题。**

**问题设计原则**：
- ✅ "你验证过XX假设吗？用什么方法验证的？"
- ✅ "如果XX条件不成立，方案还有效吗？"
- ❌ "你觉得这个方案有风险吗？"（太泛）
- ❌ "为什么不考虑另一个方向？"（不是追问，是建议）

### Phase 4: 三维挑战

从三个维度系统性地挑战方案。

**输出格式**：
```
### 市场/客户维度
- {挑战点}
### 执行/资源维度
- {挑战点}
### 竞争/替代维度
- {挑战点}
```

**三维度定义**：
1. **市场/客户维度**：需求真伪、付费意愿、市场规模、获客成本、留存
2. **执行/资源维度**：团队能力、时间窗口、资金、关键路径依赖
3. **竞争/替代维度**：现有竞品、潜在进入者、替代方案、护城河

**操作**：
- 每维度 2-3 个具体挑战点
- 挑战点必须基于方案的具体内容，不能是通用模板

### Phase 5: 重构 + KPI

基于前4个Phase发现的漏洞，提出方案应如何调整，并定义可验证的KPI。

**输出格式**：
```
### 重构建议
1. {关键调整1}
2. {关键调整2}

### 必验KPI
- {KPI1}：{目标值}，{验证方法}，{时限}
- {KPI2}：{目标值}，{验证方法}，{时限}
```

**操作**：
1. 重构建议不超过3条，优先修复Phase 2中发现的致命问题
2. KPI必须是可量化、可验证的，每个KPI包含：目标值 + 验证方法 + 时限
3. KPI类型优先级：用户行为数据 > 收入数据 > 主观反馈

### Phase 6: 案例佐证

用真实世界的成败案例支持上述分析。

**输出格式**：
```
### 相似案例
- **{公司/产品}**：{简要描述} → {结果}。启示：{与当前方案的相关性}
```

**操作**：
1. 提供1-2个案例，优先选行业相近的
2. 案例可以是成功或失败的，但必须说明与当前方案的相似性和差异性
3. 如果找不到真实案例，明确说"未找到高度相关的已知案例"，不编造

**失败处理**：
- 如果找不到高度相关的已知案例 → 输出"未找到高度相关的已知案例"，不降级为模糊类比
- 如果只有部分相关的案例 → 标注"相关性：中等"，并说明差异点

## 关键约束

1. **苏格拉底追问上限5个**——超出即为过度审查，失去聚焦
2. **禁止建议替代方案**——蓝军的职责是暴露问题，不是做新方案。不要输出"你应该改成XX"
3. **禁止模糊评价**——每条挑战必须指向具体的逻辑漏洞或未验证假设，不能是"这个方案风险较高"
4. **案例不编造**——找不到真实案例时，诚实标注"未找到高度相关的已知案例"
5. 🔴 **CHECKPOINT·grill-me 增强：输出先确认方案理解**——Phase 1完成后，必须用 grill-me 决策树确认法（2-3 个核心维度）向用户确认方案核心理解。如果用户纠正你的理解，回到 Phase 1 重新还原后再继续
6. 🔴 **CHECKPOINT：审查完成不替决策**——全篇输出完毕后，用一句话总结最关键的3个风险信号，但不给"应该做/不应该做"的结论

## ⛔ 反例与禁止操作

| # | 禁止操作 | 原因 | 正确做法 |
|---|---------|------|---------|
| 1 | 输出"建议放弃这个方案"或"应该改成XX" | 蓝军不替代决策者 | 只暴露逻辑断层，让决策者自己判断 |
| 2 | 苏格拉底问题超过5个 | 超出聚焦上限，用户无法逐个回应 | 只保留5个最致命的问题 |
| 3 | 用模板化语言填充死因（"市场风险""执行风险"） | 没有信息量，浪费审查机会 | 每条死因必须包含具体的数字或因果链 |
| 4 | 编造不存在的案例 | 损害信用，一旦被识破全篇失效 | 诚实标注"未找到高度相关案例" |
| 5 | 跳过 Phase 1 直接批方案 | 理解错误则全篇作废 | 必须先确认本质理解 |
| 6 | 输出字数膨胀（>2000字） | 长文降低用户阅读意愿，核心信息稀释 | 保持精炼，每个挑战点一句话说清

## 常见陷阱

| # | 陷阱 | 为什么是问题 | 正确做法 |
|---|------|-------------|---------|
| 1 | **变成"挑刺"而非"审查"** | 无建设性的否定失去审查价值 | 每个挑战点指向具体假设，并提供验证路径 |
| 2 | **超出5个苏格拉底问题** | 问题过多失去焦点，用户无法逐个回应 | 只保留5个最关键的问题，优先追问致命假设 |
| 3 | **替用户做决策** | "你应该放弃这个方案"不是审查 | 只暴露逻辑断层，不替代决策 |
| 4 | **Phase 2 死因太表面** | "竞品太多"没有信息量 | 追问"Why"直到触及根因 |
| 5 | **跳过Phase 1直接批方案** | 没理解本质就开始批，容易批错靶子 | 必须先还原本质，确认理解一致 |
| 6 | **KPI不可验证** | "用户满意度提升"无法客观度量 | 每个KPI写清楚量化方法 |

## 审查后重构（非蓝军职责，但常见后续需求）

蓝军审查暴露数据矛盾/逻辑断层后，用户常要求「根据你的建议，帮我重构方案」。这不是蓝军的职责范围，但有一个系统性的重构方法：

**运营容量倒推法**（见 `references/reconstruction-pattern.md`）：
1. 从运营容量上限倒推（日轮次 × 单轮容量 = 日产能上限）
2. 日产能上限 × 天数 × 客单价 = 月度营收
3. 月度营收累加 = 总量目标
4. 确保拆分=总量，消除数据矛盾

重构输出应创建为飞书在线文档（非 chat 长文），使用 `feishu-doc` 技能归档到知识库。

## 验证清单

- [ ] Phase 1 本质判断是一句话，不是一段话
- [ ] Phase 2 死因3-5条，每条含因果链
- [ ] Phase 3 问题 ≤ 5个，有递进关系
- [ ] Phase 4 三维度均有具体挑战点
- [ ] Phase 5 KPI全部可量化验证
- [ ] Phase 6 案例真实，标注了相似性和差异性
- [ ] 全篇没有"你应该改成XX"类的替代方案建议
