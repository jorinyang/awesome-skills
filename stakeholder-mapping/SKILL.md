# 干系人分析与沟通计划

> 识别所有会影响或被影响的人，用 Power×Interest 矩阵定位，为每类干系人制定差异化沟通策略。

---

## Power × Interest 矩阵

```
                    高 Power
                       │
  ┌────────────────────┼────────────────────┐
  │                    │                    │
  │  Keep Satisfied    │  Manage Closely    │
  │  (保持满意)         │  (紧密管理)         │
  │                    │                    │
  │  定期更新           │  频繁1对1           │
  │  关键事项升级        │  参与决策           │
  │  不要过度沟通        │  提前征求意见        │
  │                    │                    │
  ├────────────────────┼────────────────────┤
  │                    │                    │
  │  Monitor           │  Keep Informed     │
  │  (关注)            │  (保持知情)         │
  │                    │                    │
  │  轻触式更新          │  定期状态更新        │
  │  按需提供            │  邀请参加Demo       │
  │  被动回应            │  收集反馈           │
  │                    │                    │
  └────────────────────┴────────────────────┘
                    低 Power
                    高 Interest ◄──────────► 低 Interest
```

## 使用步骤

### 1. 识别干系人

列出所有相关的个人和群体：

- 决策者（高管、投资人、委员会）
- 执行者（项目经理、团队成员）
- 影响者（技术专家、行业意见领袖）
- 用户/客户（直接使用者、购买决策者）
- 监管方（合规、法务、审计）
- 供应商/合作伙伴

### 2. 分类：Power × Interest

对每个干系人回答两个问题：

- **Power（权力/影响力）**：他们能影响决策、资源、或结果吗？（高/低）
- **Interest（利益相关度）**：项目对他们影响多大？他们有多关心？（高/低）

### 3. 按象限制定策略

| 象限 | 策略 | 频率 | 方式 | 关键信息 |
|------|------|:---:|------|---------|
| **Manage Closely** (高Power+高Interest) | 深度参与 | 每周 | 1对1、决策会议 | 项目进展、风险、需要他们决策的事项 |
| **Keep Satisfied** (高Power+低Interest) | 保持满意 | 双周/月 | 简报邮件、季度汇报 | 项目整体状态、关键里程碑、需要他们批准的节点 |
| **Keep Informed** (低Power+高Interest) | 保持知情 | 每周/双周 | 群组更新、Demo邀请 | 项目进展、功能变化、可参与的测试或反馈机会 |
| **Monitor** (低Power+低Interest) | 轻触关注 | 按月/按需 | 公告、新闻信 | 项目大致方向、里程碑完成通知 |

### 4. 输出沟通计划表

```
| 干系人 | 角色 | Power | Interest | 策略 | 频率 | 渠道 | 核心信息 |
|--------|------|:-----:|:--------:|------|:----:|------|---------|
| 张总   | CEO | 高 | 高 | 紧密管理 | 每周 | 1对1会议 | 决策点+风险+资源需求 |
| 李经理 | 技术负责人 | 高 | 高 | 紧密管理 | 每周 | 技术评审 | 架构决策+技术风险 |
| 王法务 | 合规 | 高 | 低 | 保持满意 | 每月 | 邮件报告 | 合规状态+变更通知 |
| 陈运营 | 用户代表 | 低 | 高 | 保持知情 | 双周 | Demo邀请 | 功能变更+反馈收集 |
| 外部顾问 | 供应商 | 低 | 低 | 关注 | 按需 | 邮件通讯 | 项目大方向 |
```

### 5. 识别潜在冲突

检查干系人之间是否有竞对利益：

| 冲突 | 干系人A | 干系人B | 调和策略 |
|------|--------|--------|---------|
| 功能范围分歧 | 产品经理（要完整性） | 工程总监（要可行性） | 分阶段交付，M1做核心+验证 |
| 节奏预期冲突 | CEO（越快越好） | 合规（必须充分审查） | 并行推进：开发+合规审查同步 |

## 关键原则

1. **尽早做**：项目启动时完成干系人分析，不等问题出现再补救
2. **动态更新**：项目推进中干系人位置会变化——有人从"Keep Informed"变成"Manage Closely"
3. **不要忽略"低 Power"**：被忽略的低Power干系人可能在你最不想的时候变成障碍
4. **沟通 ≠ 通知**：Manage Closely 需要双向对话，不是单向报告
5. **信使比信息更重要**：不同的干系人需要不同的人去沟通——CEO 更愿意听另一个 CEO 说，不是基层 PM

---

## 常见反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 只关注高Power | 低Power高Interest的人被忽视后成为阻力 | 全面扫描 |
| 所有人都Manage Closely | 浪费精力，高Power的人觉得被过度沟通 | 差异化策略 |
| 沟通千篇一律 | 技术人收到业务汇报，业务人收到技术细节 | 按角色定制信息 |
| 发现冲突但不调和 | 冲突积累最终在关键节点爆发 | 提前识别、主动调和 |
